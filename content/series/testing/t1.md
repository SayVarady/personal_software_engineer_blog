## The Pyramid Everyone Draws, and Why It Stops Helping

Every testing talk starts with the same triangle: a fat base of unit tests, a thinner band of integration tests, and a tiny cap of end-to-end tests. It's a useful picture the first time you see it — it tells you "write more small tests than big ones." But after a few years of shipping real features, I noticed the pyramid stops being useful advice and starts being a shape people optimize for its own sake. Teams chase a unit-test count instead of asking what those tests actually protect against.

The problem isn't the pyramid's shape. It's that "unit" was never a precise word. A unit test that mocks every collaborator can pass while the feature is completely broken, because it never touches the boundary where things actually go wrong — the seam between your code and the database, the filesystem, another service, or someone else's assumptions about your API.

## Boundaries, Not Layers

The distinction I've come to care about isn't "how big is the thing under test," it's **where the boundary is**. A boundary is any place behavior is a contract, not an implementation detail: a repository interface, an HTTP endpoint, a queue message shape, a public function signature other teams call.

Tests that sit *at* a boundary catch the bugs that matter — wrong status code, a field renamed without updating the consumer, a null case nobody handled. Tests that sit *inside* a boundary, asserting on private implementation details, break every time you refactor and catch almost nothing real. I've deleted more of the second kind than I've written of the first, and the suites got both faster and more trustworthy.

This is why the pyramid's layer names (unit/integration/e2e) matter less than asking, for any given test: *if this fails, does it tell me something a user or another engineer would actually feel?*

## A Shape That's Held Up in Practice

What I reach for now isn't a pyramid, it's closer to a small set of boundary tests per feature, backed by fast in-process tests for pure logic, with a handful of true end-to-end tests reserved for the paths that would be a real incident if they broke — checkout, auth, payment webhooks. Everything else gets tested at the nearest boundary and no lower.

Later chapters in this series get concrete about each of these — contract tests between services, property-based tests for the logic that's too combinatorial to enumerate by hand, and how to keep test infrastructure itself from becoming the thing you're afraid to touch.

## Key Takeaways

- The pyramid's *shape* (more small tests than big ones) is still fine advice; its *layer names* are not a checklist to satisfy.
- Ask "does this test sit at a boundary that matters?" before asking "is this a unit test?"
- Tests on private implementation details break on refactor and catch little — delete them without guilt.
- Reserve true end-to-end tests for paths where a failure would be a real incident, not for everything.
