## Before the Framework, There's a Wire

Every framework — Laravel, React, Rails, whatever comes next — is a set of conveniences layered on top of the same underlying reality: a client asks for something, a server answers, and the answer travels over a network in a very specific, very old format. If you learn the framework first, that reality stays invisible, and the moment something breaks in a way the framework doesn't paint over, you're stuck. If you learn it first, the framework stops looking like magic and starts looking like a shortcut for things you already understand.

So before anything else: what actually happens when you type a URL and hit enter?

## Client, Server, and the Illusion of "Connecting to a Website"

There's no single thing you "connect to." Your browser (the client) resolves the domain name to an IP address via DNS — a distributed lookup, not a single database — then opens a TCP connection to a server at that address, usually on port 443 for HTTPS. The server is just a process, listening on that port, waiting for requests it knows how to answer. "The website" is really: DNS record + server process + whatever code that process runs to decide what to send back.

This matters practically the first time DNS is stale, or the server process has crashed but the machine is still up, or you're debugging why `localhost:3000` works but your phone on the same wifi can't reach it. Those aren't framework bugs. They're this layer.

## Request In, Response Out

Once connected, the browser sends an HTTP request: a method (GET, POST, ...), a path, headers, maybe a body. The server sends back an HTTP response: a status code, headers, a body. That's the entire contract. Every framework route, every controller, every API endpoint you'll ever write is just code that runs between "a request arrived" and "send this response." Learning to read a raw request/response — what a status code actually promises, what a header actually means — pays off every single time you debug a network tab instead of guessing.

## Stateless by Default

HTTP itself has no memory. Each request is independent; the server doesn't inherently know request #2 came from the same browser as request #1. Everything that feels like "the server remembers me" — being logged in, a shopping cart persisting — is built on top of HTTP, usually with cookies carrying an identifier the server looks up. Frameworks make sessions and auth feel automatic. Knowing it's not automatic, that it's a deliberate mechanism bolted onto a stateless protocol, is what lets you reason about session bugs, CSRF, and "why did I get logged out" instead of treating them as framework mysteries.

## Key Takeaways

- A "website" is DNS + a listening server process + code deciding what to respond with — not one monolithic thing.
- Every route/controller you write is code between "request arrived" and "response sent." That contract predates every framework.
- HTTP is stateless. Anything that feels persistent (login, carts) is a mechanism built on top, not a property of the protocol.
- Debugging at this layer (DNS, connection, raw request/response) solves problems frameworks can't paint over.
